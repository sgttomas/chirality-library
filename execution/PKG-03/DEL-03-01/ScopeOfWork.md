# Support current localities with actual reusable tools

## Purpose and Objective Traceability

A maintainer can form a deliverable locality, check it, validate its scope and
ask what a deliverable needs, feeds or is touched by, using commands the
Library already holds; and what the instructions say about each command (what
it takes, what it requires, what it writes, how it fails and where it stops)
is what the command does. This deliverable contributes three things to that
result: the utilities that prepare a locality, check its structure and
validate its scope; the deliverable queries; and the usage contracts for those
utilities and for the workflow resolver, at the guides and caller instructions
where a maintainer reads them.

Its allocation is the DEL-03-01 card of the
[accepted decomposition](../../_Decomposition/PROJECT_DECOMP.md), with the
interfaces in that document's §9. It serves
[PRD](../../../docs/PRD.md) objectives O1, O2, O4 and O5.

## Deliverable Definition — Ontology

A **utility** is executable, repeatable behaviour. A **usage contract** is the
passage in a guide or caller instruction that states a utility's invocation,
inputs, dependencies, outputs, write effects, failure behaviour and limits.
The two are separate outputs and each is examined against the other.

A **locality** is `execution/PKG-nn/DEL-nn-nn/`, holding `ScopeOfWork.md` and
`deliverable.yaml`. A **declaration** is a consumer's `deliverable.yaml`: its
id, its needs, and its code and check pointers.

- **CLM-002** — The **current route** is selected by passing `--current` to `scaffold_package.sh`, `scaffold_deliverable.sh` and `check_min_viable_fileset.sh`. The same entry points called without the flag are the **legacy interface**: the phase-folder and control-file layout, kept for projects that adopted it, to which the four-document conversion tools in `tools/scope_of_work/` also belong. On the current route a locality is **prepared** when its folder and a `deliverable.yaml` carrying the accepted id and name exist, and **authored** when it also holds a `ScopeOfWork.md` whose front matter names the same package and deliverable. Three checks give three different results. The **prepared check** (`check_min_viable_fileset.sh --current --prepared`) passes a prepared locality without requiring a scope. The **authored check** (the same command without `--prepared`) requires the scope and its matching identity. **Contract validation** (`validate_scope_of_work.py`) reports which format a deliverable folder resolves to and whether its `ScopeOfWork.md` meets `SOW_V1`, the contract format of the scope-of-work method.
- **CLM-003** — A **query** computes a view from the declarations as they stand in the working tree when it runs, uncommitted ones included, and states its **basis**: the `HEAD` revision and the working-tree changes it observed. `check` reads every declaration; `neighborhood` gives one deliverable's inputs, outward obligations and consumers; `impact` follows consumers transitively; `touches` matches the paths of a Git change against code paths and localities; `dag-diff` compares the declarations at a named revision with the working files. A query result is an observation. It is not a supplier commitment, a completion mark or a decision.

- **OUT-001** — The locality setup and contract-validation utilities, with their maintained regression cases: `tools/scaffolding/current_locality.py`, `tools/scaffolding/scaffold_package.sh`, `tools/scaffolding/scaffold_deliverable.sh`, `tools/validation/check_min_viable_fileset.sh`, and the validators and checklist tools in `tools/scope_of_work/`. Serves SOW-0009, SOW-0024 and OBJ-001, OBJ-002, OBJ-005.
- **OUT-002** — The deliverable queries at `tools/deliverables/`, with their maintained regression cases. Serves SOW-0015, SOW-0024 and OBJ-001, OBJ-004, OBJ-005.
- **OUT-003** — The usage contracts: `tools/deliverables/README.md`; `tools/workflow_runtime/README.md`; the preparation, checking and query commands in `workflows/project-setup/resources/current-project.md`; `.agents/skills/preparation/`; the tool policy and command statements in `workflows/scope-of-work/`; and `workflows/dependency-extract/resources/tools.md`. Serves SOW-0009, SOW-0015, SOW-0024 and OBJ-001, OBJ-002, OBJ-004, OBJ-005.

The hosted check harness and the profile that selects test suites for a change

## Completion and Reliance Basis — Epistemology

- **REQ-001** — On the current route, package preparation creates the numeric package folder and nothing else. Deliverable preparation creates the numeric deliverable folder and a `deliverable.yaml` carrying the accepted id, the accepted name and an empty needs list. Preparation never overwrites, moves or reinitialises a file that exists, an empty file included; it reports the paths it created and only those; and running it again changes nothing. It refuses, without writing: an identity that is not an accepted numeric package or deliverable identity; a deliverable placed under a package folder of a different number; an existing declaration or scope whose identity disagrees; and a path already occupied by something that is not the expected folder or regular file, a link included. It creates no `ScopeOfWork.md`, phase directory, `_STATUS.md`, `_CONTEXT.md`, `_REFERENCES.md`, `_SEMANTIC.md`, memory file or setup receipt. The current route requires Python 3 and PyYAML, and `PYTHON` selects the interpreter. The legacy interface behaves as it did before the current route existed. Source: SOW-0024; PRD R08, §6.3; decomposition card.
- **REQ-002** — Each query derives its result from the owning declarations and from nothing stored beside them. It writes nothing and prints JSON that names its basis and cites, for every relationship, the declaring file and the need's position in it. Each declared need is returned as its own row with every field the consumer wrote, so that two needs between the same pair, a preliminary and a final use, a reciprocal pair, a non-gating need and a stated hold all stay distinct. Paths and globs in a declaration are read relative to the project named by `--project`, and none is followed outside it. A missing supplier, an external or unknown source, an absent path and a cycle are reported as observations and do not fail the query. Malformed input is reported as an error with a failing exit and whatever result remains usable. No query assesses whether a condition is met or suitable, runs a referenced check, lifts a hold, or reports completion, readiness or acceptance. `dag-diff` reads its baseline from the named Git revision and the present state from the working files. Queries require Python 3, PyYAML, Git and a resolvable `HEAD`; `touches` given a pull request additionally needs an authenticated `gh` and network access, and no other query does. Source: SOW-0015; PRD R03, R09, R10, §6.1.
- **REQ-003** — Each usage contract in OUT-003 states, for every command it shows, the invocation, the inputs, the dependencies, the outputs, the write effects, the failure behaviour and the limits, and what it states is what the command does. It keeps apart a structural check, contract validation, evidence that a command behaves as stated, and a person's decision that work is suitable. It states the capability that is unavailable when a dependency is missing and the fallback permitted: without the query command, PyYAML, Git or `HEAD`, the declarations and sources are inspected directly and the limit of that inspection is stated; no Git-free query is offered. The resolver's contract says that the resolver reports the selected role, methods, resources and composed policy, that it launches no agent and grants and enforces no permission, that enforcement is the host's, and that `--brief` needs PyYAML for a JSON brief as for any other. Source: SOW-0009; PRD R05, R13.
- **REQ-004** — The product is the existing utilities, repaired at their maintained homes where a behaviour disagrees with its usage contract or with this scope. Behaviour required by REQ-001 and REQ-002 that touches what is written, preserved or kept inside the project (preservation of existing files, identity disagreement, occupied or linked paths, paths that escape the project, malformed declarations) has focused regression cases in the suite beside its utility; other meaningful cases are kept in those suites. Source: SOW-0024; PRD §2.2, R12, R17; decomposition card.
- **REQ-005** — Every utility in OUT-001 and OUT-002, and every resource its usage contract names, is usable from the repository alone: no sibling checkout, dated run directory, private input, credential or companion is required, and each real dependency is declared. The Library's existing Git, search, review, release, validation and scheduling foundations keep working. Fixtures, examples and regression cases hold no credentials and no private consumer data. Source: SOW-0024; PRD §1, R13, R17.
- **REQ-006** — This deliverable shall perform no act owned by another deliverable: navigation and the workflow catalog and index belong to `DEL-01-01`; the maintenance route and the revision of a role, a method or a tool belong to `DEL-02-01`; the shared-reference repair belongs to `DEL-02-02`; what remains of the former evaluator belongs to `DEL-03-02`; the reconciliation method and the formation of localities and needs belong to `DEL-04-01`; the accepted decomposition and the reflective method belong to `DEL-04-02`; obtaining, compatibility with a named consumer and publication belong to `DEL-05-01`, as CLM-004 allocates. A utility supports setup, need authoring and reconciliation; it does not perform them for the contributor.
- **REQ-007** — The product contains none of the things listed as outside it. A tool of that kind enters only for a demonstrated gap in these operations and by the owner's decision. An interface a named consumer reads (the declaration format, the query JSON, the resolver result) changes incompatibly only after a supported path or coordinated adapter exists for that consumer. Source: SOW-0024; PRD §1, §2.3, R13, R17, §6.1; decomposition card.

- **AC-001** — In an empty execution root, the two current preparation commands leave the numeric package folder, the numeric deliverable folder and a `deliverable.yaml` with the accepted id, the accepted name and an empty needs list, and report as created the paths they created and only those. Run over a locality that already holds files, they leave every existing byte unchanged and report nothing created. Each case REQ-001 says is refused fails with a message naming the disagreement and writes nothing. In no run does a file or folder REQ-001 excludes appear. The unflagged commands produce the legacy layout unchanged. Verify by VER-001.
- **AC-002** — The prepared check passes a prepared locality that has no scope and fails one whose declaration is absent or disagrees with the folder. The authored check fails a locality with no scope, fails one whose scope names another package or deliverable, and passes one whose identity agrees. Contract validation passes a contract that has the required front matter, the six parts in order, every referenced id defined and every output, acceptance criterion and verification mapped in the matrix, and fails with a stated reason a contract that breaks any one of these. It names the format the folder resolves to and fails closed: a valid sole `ScopeOfWork.md` resolves as `SOW_V1` and a complete legacy four-document kit alone as the legacy format, while a missing, partial or invalid contract resolves as invalid and both formats together as ambiguous unless the conversion's migration authority is supplied. A pass from one of the three is never reported as a pass of another, and none of them creates, requires or changes a `_STATUS.md` or a legacy document kit in a current locality. Verify by VER-002.
- **AC-003** — For a set of declarations, each query returns the relationships those declarations state and no others, each with its declaring file and position, under a basis naming `HEAD` and the working-tree changes. An uncommitted declaration is included. Distinct needs between the same pair appear as distinct rows with their fields intact. A cycle, a missing supplier, an external or unknown source and an absent path are reported and the query exits successfully; a malformed or duplicated declaration yields a stated error, a failing exit and the rest of the result. References resolve against the named project and never outside it. Nothing in any result states that a condition is met, that work is ready or complete, or that a referenced check ran. Verify by VER-003.
- **AC-004** — Every command shown in a usage contract of OUT-003, run from the stated location with the stated prerequisites, takes the inputs, writes the files, prints the output and exits as the contract says. With a stated prerequisite absent, the failure is the one stated and the stated fallback can be followed. No behaviour of the command that a caller must know to use it is missing from its contract. The resolver's contract and the resolver agree that a denied command is reported as denied and is neither run nor blocked by the resolver. Verify by VER-004.
- **AC-005** — The behaviours REQ-004 names have maintained regression cases in the suite beside their utility, among them cases for preservation of existing files, identity disagreement, an occupied or linked path, a path that escapes the project and a malformed declaration, and those suites pass, as do the suites of the validation foundations named in the Ontology. The tool directories of OUT-001 and OUT-002 hold no helper, framework or adapter that repeats what an existing utility does. Verify by VER-005.
- **AC-006** — In a tree extracted from an archive of the repository, with no sibling checkout, credential or network, preparation, the prepared and authored checks, contract validation and the resolver run as their contracts say with only their declared dependencies; the queries, which need Git and `HEAD`, fail there in the stated way and their stated fallback can be followed. The fixtures, examples and regression cases of OUT-001 and OUT-002 pass the credential scan. Verify by VER-006.
- **AC-007** — The utilities and usage contracts contain nothing CLM-004 allocates to another deliverable and nothing REQ-007 excludes, and no change to them has altered incompatibly an interface a named consumer reads without the supported path or adapter REQ-007 requires. Verify by VER-007.

## Production and Verification Method — Praxeology

Choices that define the product:

- The current route is chosen by an explicit flag on the existing entry
  points. There is no second set of commands, and no flag means the legacy
  interface.
- Preparation makes structure and never content. A scope is authored through
  the scope-of-work method and needs through dependency-extract.
- Consumers declare; everything else is derived. A query reads the
  declarations each time it runs and keeps nothing between runs.
- The utilities are local and deterministic. They use no network, except
  `touches` when it is given a pull request, and no model.
- A defect is repaired in the utility or the contract where it lives. A new
  tool is not the remedy for a disagreement between an existing tool and its
  contract.

- **VER-001** — Executable check (observes the files and folders present after preparation, against the set placed before it and the set REQ-001 names): in a temporary execution root run the two current preparation commands on an empty root; again over a locality holding a pre-placed empty file, a declaration and a scope; and once for each refused case in REQ-001. Compare the bytes of every pre-placed file before and after, the paths present with the paths reported as created, and the exit status and message of each refusal. Run the unflagged commands and compare the layout they create with `.agents/skills/preparation/references/legacy-scaffold-contract.md`.
- **VER-002** — Executable check (observes the exit status and message of each of the three checks on localities built for the case) and comparison with a named reference (the contract format in `workflows/scope-of-work/WORKFLOW.md`): build a prepared locality with no scope, one with a missing declaration, an authored one whose identity agrees and one whose identity disagrees; write by hand, from the method's statement of the format, one contract that meets it and one for each single rule broken; and build folders holding a legacy kit alone, a partial kit, and a kit beside a contract. Run the three checks on each and compare with AC-002, and list the locality's files before and after. Then run the authored check and contract validation on the Library's own localities.
- **VER-003** — Executable check (observes the JSON and exit status each query returns for declarations written for the case): in a temporary Git repository write declarations holding two distinct needs between one pair, a reciprocal pair, a cycle, a non-gating need, a missing supplier, an external, a document and an unknown source, an absent path, a path that escapes the project, a malformed file and a duplicated id, with one declaration left uncommitted and one earlier revision tagged. Read the expected relationships by hand from those declarations and compare them with what `check`, `neighborhood`, `impact`, `touches` and `dag-diff` return, including basis, source citations and exit status. Then run `python3 -m tools.deliverables --project . check` and one `neighborhood` on the Library's own localities and compare the rows with their declarations.
- **VER-004** — Judgment by a reader who did not write the contract (runs each command a usage contract shows and compares what happens with what the contract says): for every contract in OUT-003, run each shown invocation from the stated location with the stated prerequisites, then with each stated prerequisite removed in turn, and record inputs taken, files written, output, exit status and whether the stated fallback could be followed. For the resolver, give it a policy that denies a command and confirm the result reports the denial and that nothing ran or was blocked. Report as unverified any statement that was not run.
- **VER-005** — Judgment by a reviewer who did not write the change under review (reads the regression suites against the behaviours REQ-004 names and the tool directories for duplicated function), with an executable check (the suites, which observe the behaviours their cases name): list each behaviour, name the case that exercises it and what that case would let pass, and run `python3 tools/run_affected_tests.py --base <base>` for the suites the change affects.
- **VER-006** — Executable check (observes the commands running in a tree extracted with `git archive` into an empty directory, with no sibling checkout, credential or network), with an executable check (the credential scan, which observes only the patterns it holds): run preparation, the two structural checks, contract validation and the resolver there with only the declared dependencies installed; run a query there and compare its failure and fallback with the contract. Run `python3 tools/validation/validate_run_record_leaks.py --base <base> --head <head>` on the change and state what the scan does not cover.
- **VER-007** — Judgment by the integration owner (reads the utilities and usage contracts against CLM-004 and REQ-007, and reads the diff of any change to the declaration format, the query JSON or the resolver result for an incompatible alteration): where one is found, confirm from `DEL-05-01`'s named-consumer evidence that the supported path or adapter exists.

## Governing Values and Decisions — Axiology

- **AX-001** — A result says what the tool observed and no more. Better is fewer results a reader could take for more than was observed: a pass read as acceptance, a present path read as suitability, an empty needs list read as completeness. That may never be gained by leaving an unknown, a cycle, an error or a partial result out of the output so that it reads more cleanly.
- **AX-002** — Reuse what is sound. Better is fewer commands, flags and files a maintainer must learn to form, check and query a locality, and fewer places where the same behaviour is implemented. That economy may never leave a behaviour this scope requires unmet, or a behaviour REQ-004 names without a regression case.
- **AX-003** — The contract and the command agree, for every caller. Better is fewer statements in a usage contract that the command contradicts when run, and fewer callers broken by a change. That may never be gained by removing a stated dependency, failure or limit from the contract so that it has less to be wrong about, or by dropping the legacy interface without its consumers' decision.
