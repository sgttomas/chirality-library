## 2. Product and intended use

A local, reusable work-and-repository evaluation workbench supplied through the Library:
command-line software, an inspectable local report and comparison, benchmark-case
support, and a selected agent workflow. A project uses it to examine how an
repository changed under the relevant conditions, whether that change justifies
the effort, and how the means of reaching useful states can improve. Repository
state change is the primary evaluative subject. Undertaking observations explain
the effort and possible means of producing that change; activity is not itself
the benefit being rewarded. State change may span several undertakings or be
examined without a complete execution record.

The purpose is better purposeful work: intelligible grounds and consequences,
adequate results, useful human attention and proportionate effort. Efficiency is
one dimension. Inquiry can validly retain the existing method, identify an
inadequate evaluation, reframe a task or return a missing decision. A positive
speed gain, an adopted change or a numerical score is not required for every use.

The initial production increment must demonstrate one supported host record route,
one named project, identified repository before/after states and one recurring
task family. Repository comparison itself must not require a host trace when the
selected question can be answered from repository sources and applicable evidence.
The combined initial demonstration still includes actual work observations. It includes:

1. Import available records, identify their provenance and coverage, and bind
   observations to the assignment where applicable, source/candidate revisions and checks.
2. Produce deterministic supported measurements and a local, evidence-linked
   inspection report, including repository state and change; expose unknowns instead
   of reconstructing missing events or unsupported state.
3. Prepare an identified case basis and compare baseline/variant trials under
   declared conditions. Use the consuming host's available execution mechanism;
   a new agent runtime is not commissioned. State the supported trial invocation
   and how actual results reach the comparison.
4. Supply a bounded evaluation workflow that connects the question, observations,
   interpretation, comparison where warranted, and usable retain/change return.
5. Demonstrate the combined capability on actual authorized work, supplementing
   it with clearly labelled fixtures for error conditions. Keep the cost of the
   collection and assessment itself visible.

The exact host/export contract, pilot project and task family remain design
inputs to establish before claiming an adapter or trial route works. A particular
host API, session export, subscription billing attribution or access to hidden
reasoning is not assumed. An inability to bind the selected host route is a
specific unmet implementation condition, not permission to substitute synthetic
fixtures for the promised actual-use demonstration.

### Repository state and change

Select identified before/after bases, or a sequence of bases, and the question,
affected holdings and intended uses to examine. A state basis can be a commit,
a captured candidate/working tree, or an issued edition. Distinguish those
subjects; record the inclusion and limits of any noncommitted material. Do not
silently collect private or unrelated local files to claim a complete snapshot.

Derive the relevant view from owning sources and observations: governing
commitments, implementation or supported behavior, reasoning and evidence,
dependency conditions, unresolved matters, and working/accepted/issued standing.
Do not create a second manual lifecycle or repository-state register. File
presence, changed-line counts and a successful merge establish neither fulfillment
nor improvement. Behavior claims require applicable examination at the identified
basis; source changes alone establish only their actual source meaning.

A comparison must expose what changed, what remained supported, what became
unsupported or inconsistent, and what changed in the grounds for reliance. For
example, an implementation can improve while its scope description stays stale;
new evidence can invalidate a prior claim without code changes; an accepted scope
extension can introduce legitimate unfinished work. Each has a different meaning
from regression or failure to complete the preceding undertaking. Preserve the
actual decisions and historical evidence, and distinguish them from present
assessment.

Relate observed work to these state changes only where the evidence supports
that relationship. Multiple contributors and intervening changes can prevent
attribution to one undertaking. A repository improvement and a more efficient
production method are different claims; evaluate them separately and examine
their relationship. Changed requirements, criteria or environments need their own
basis rather than a silently shared success score. Missing context remains a
limit on the comparison, not a fabricated explanation.

### State conditions, local goals and learning

Begin with the identified starting state, the intended change, the conditions
under which it would be useful, and the effort and consequences of reaching it.
Examine the actual resulting state and the grounds for saying those conditions
hold. Judge whether the change justifies that effort under the selected purpose,
constraints and uncertainties. Do not equate change volume or fewer operations
with improvement, or assume that every useful consequence has a numerical value.

As understanding develops, turn relevant conditions of a useful state change into
more specific local goals. For example, a change to an instruction can need an
actual caller to remain usable, its examination to address the changed behavior,
and its scope description to agree with the result. Those conditions can become
bounded objectives for connected contributions, rather than a generic demand to
produce more artifacts or finish more tasks.

A hypothesis can propose that a particular method, context selection, tool or
coordination arrangement will establish one of those conditions more effectively.
Bind the hypothesis, the expected state consequence, applicable examination and
resource conditions. Try the selected intervention, then compare the achieved
state change and total relevant effort. Preserve failures, contrary findings and
unknown attribution. A local goal is useful through its contribution to the
wider state, including effects on neighboring work; local satisfaction alone is
not proof that the undertaking improved.

The resulting evidence may refine the goal, the conditions, their representation
or the proposed means. Such revision keeps the preceding basis identifiable and
respects authority for changed commitments. Do not silently replace criteria to
turn a failed attempt into success. A consequential unexpected finding can warrant
a different decision, with its actual subject and grounds made explicit.

A justified retention decision or improved grounds for reliance can matter even
when executable bytes remain unchanged. Identify the real changed understanding,
evidence or resolved condition and its use; require no cosmetic repository edit
or new receipt merely to manufacture a measurable delta. Proxy feedback, where
selected, derives from these specific state conditions and their demonstrated
relationship to useful progress, and remains open to correction.

### Operating arrangement

Software collects/imports and calculates. Agent 0 selects a bounded evaluation
question and its observation/write/resource limits with the human. Agent 0 may
dispatch a small assessment directly to TASK. WORKING_ITEMS owns a larger study
through case preparation, bounded trials, examination and integration of returns.
An assessor's interpretation remains an evidence-supported claim; a different
agent identity alone does not establish independent grounds.

Reconciliation can bind the actual candidate and affected-use evidence when
evaluation is activated. It is not a mandatory benchmarking station. Evaluation
that is not part of the production undertaking's agreed completion conditions
may continue separately without holding otherwise adequate work. Human judgment
informs purpose, relevance and consequential choices throughout; agents continue
ordinary authorized investigation and repairs without repeated approval prompts.

### First-increment boundaries

- No permanent observer agent, global activity census, central project controller,
  mandatory telemetry for every task, or compulsory companion installation.
- No universal quality/reward score, automatic change to acceptance criteria,
  autonomous model-training loop or automatic adoption of proposed methods.
- No promise to attribute all elapsed time, cached tokens, actual spending or
  private human attention from incomplete host observations. Observation,
  derivation, interpretation, decision and accepted reliance remain distinct.
- No automatic consumer rollout, remote notification, publication or engineering
  qualification. App v4 and SWBPIPE retain independent authority and chosen bases.
- No private operational logs or credentials in the public Library. Local data
  stays within the selected consumer boundary; publish only cleared examples.
- No claim that a trace exhausts an undertaking or that a fixed case represents
  all future use. Material changes in purpose, environment or criteria receive
  a distinct basis and a renewed comparability assessment.

## 7. Verification and unresolved implementation conditions

Before judging the new capability fulfilled, establish:
- Faithful import/binding and explicit missing or malformed evidence behavior.
- Correct identity and coverage for repository before/after states; differences
  in source, behavior, evidence and standing remain distinguishable. A repository
  comparison can run without an undertaking trace where that is adequate.
- State-change findings identify their sources and limits, distinguish unfinished
  newly accepted scope from regression, and preserve unknown causal attribution.
- Correct treatment of retries, parallel work, changing goals, cached usage and
  other selected measures; no unsupported duration, cost or causal attribution.
- Actual result examination and scrutiny of the oracle/rubric, not self-reported
  completion or agreement among agents alone.
- Comparable case basis and conditions; failures and repairs included, variation
  and selection limits visible, no requirement that a proposed variant wins.
- A recipient can inspect the report and trace material findings to their grounds.
- Trace a selected state-change condition into a local goal or improvement
  hypothesis, then examine its actual contribution to repository change and
  relevant effort; preserve negative findings and any changed basis.
- One real combined use supports a warranted decision, with collection/assessment
  burden considered. Reframing or justified retention is an admissible result.

Open design conditions: supported host/export and execution interface; authorized
pilot case/data; outcome examination appropriate to that task family; persistence
and retention boundaries; comparable trial conditions and resource budget. These
must be bound before dependent implementation/claims, but do not prevent review
of the proposed product and allocation. No numeric performance threshold or
universal reward formula is proposed without a task-specific basis.

The four perspectives remain mutually corrective: the representation may need
revision; the evaluator's grounds can be inadequate; the working sequence may
change; and resource savings may trade against useful inquiry, maintainability
or human attention. None requires four reports, a permanent monitoring hierarchy
or automatic changes to a consumer's criteria.
